# 批量执行与交接

## 每款商品一条记录

记录可放在 `商品数据/_work/`，也可在同一轮工作中随进度维护。按竞品 URL 区分商品，后续所有文件、模板和链接都靠这一对应关系核对。

| 阶段 | 保留的状态 |
|---|---|
| 接单 | 原始竞品 URL、用户确认的平台和店铺、本轮审查要求和绑定方式 |
| 采集 | 商品关键词、素材路径、`商品装修说明.md`、成功使用的清单路径、轮播与详情媒体数、失败媒体的来源及替代路径 |
| 单品 CSV | 原始 URL、采集任务 ID 或对应结果、已验收的 CSV 路径 |
| Phalanx 录入 | CSV 路径、上传映射配置、对应商品的导入结果 |
| Phalanx 发布 | 对应的商品、目标平台和店铺、逐款发布结果 |
| 1688 以图搜同款 | 所用商品图、搜图结果、候选链接与货源确认状态 |
| Phalanx 采购与 ERP | 采购来源、实际提交值、商品内部 ID、更新结果 |
| 店铺商品核对 | 目标店铺、后台查找结果、匹配的商品 ID 或后台链接 |
| 主题 | 已核对的店铺后台域名、主题 ID、默认底稿、模板名、上传内容回读结果 |
| 商品 | 我方商品标题、商品 ID、后台编辑链接、完整目标模板路径、绑定回执或回读证据、实际预览结果 |
| 完成 | 已核对的预览 URL、竞品 URL、新素材目录和已填写各步进度的 `商品装修说明.md` |

批量任务按商品分别更新各自的说明文件，每步验收后写入该商品的实际完成日期。

店铺信息未齐时只问缺项。比如用户只回「SHOPLINE」，继续问店铺即可。竞品全名与我方全名不一致时，先搜辨识度高的关键词，回收每个结果的标题和编辑页 ID；唯一匹配才继续。多个相似结果只汇总问一次。

## 最快的顺序

1. 并行打开公开竞品页，逐页一次性批量提取。浏览器导航偶有超时但页面已加载，先看当前 URL 和标题。几页同时加载导致工具超时时，重新取得已打开的标签页，继续独立读页面。
2. 各商品使用不同清单和输出目录，调用采集脚本并发下载。某款外部媒体失败时先处理已能完成的其他款；用浏览器取该资源的原始字节再重跑本款。不要同时让两个进程写同一最终商品目录。
   本地采集验收后，按第 2 步逐款核对单品采集任务，分别导出 CSV 到各自目录。
   取得 CSV 后，按第 3 步将对应商品录入 Phalanx，逐款记录导入结果。
   录入成功后，按第 4 步将商品发布到各自对应的店铺，逐款记录发布结果。
   第 4 步发布成功后，第 5 步搜货源和第 6 步后台核对可并行。货源确认后接第 5a 步。店铺核对成功后可继续第 7–9 步。第 6 步受阻时只暂停相应商品和店铺的装修。
3. 按店铺和主题分组。第 6 步通过后，用对应平台的主题 CLI 拉取第 7 步所需的底稿和已有专用模板。同主题且无中间审查时，分别生成暂存文件，汇总一次上传与回读，逐个验收。共享 CLI 的切店、远端推送及本次回读按组串行。同一 SPU 的全量更新也串行。
4. 按第 9 步的授权和入口逐个绑定、回读。走后台时用第 6 步保存的商品编辑直达链接，上传结束后再打开。前台效果可以并行核验，结果按商品 ID 和 URL 对回记录。
5. 每款在本轮范围内的步骤都验收后，可独立交付。完整装修须同时通过第 5a 步和该款各目标店铺的绑定及预览，才标记目录完成。其他商品失败时不影响已验收的商品。

## 中断后从已验收的位置继续

| 已确认的状态 | 恢复动作 |
|---|---|
| 清单已导出，部分媒体下载失败 | 保留同一清单和顺序。只补失败媒体，再运行保存脚本。 |
| 素材已验收，CSV 待交付 | 核对说明和已有采集任务，从第 2 步继续。 |
| 素材和 CSV 已验收，尚未录入 Phalanx | 复用各自的 CSV，从第 3 步继续。 |
| Phalanx 已录入，尚未发布 | 按确认的目标店铺，从第 4 步继续。 |
| Phalanx 显示发布成功，搜图和店铺商品均待核对 | 并行推进第 5 步和第 6 步。 |
| 搜图结果已记录，采购资料待补 | 核对选源及数据，确认后做第 5a 步。可独立续跑店铺侧。 |
| 目标店铺已核对到商品，尚未有专用模板 | 从第 7 步继续。 |
| 推送结果不明 | 先回读该模板路径。已有正确内容时直接进入绑定；缺失或不同时只处理对应模板。 |
| 后台填写后不确定是否已保存 | 先核对当前页面的未保存提示，再回读对应商品。已绑定正确模板时直接核对预览。 |
| 已绑定，目录待标记 | 验收预览并检查本轮剩余步骤。都满足后进入第 10 步。已有 `1-` 时复用该目录。 |

一次 CLI 列表能核对店铺和主题就够了。目标模板已回拉并通过整份 JSON 比对后，无需重新拉同一份。只有平台结构、页面内容或实际状态不匹配时才启用对应的排查分支。

浏览器只有一个实例：全流程共用 agent 专用 profile（`~/.cache/agent-browser`，CDP 9223）。子代理连同一个实例、只开自己的标签页，不要各自 `agent_browser.py` 起新实例——同一 profile 不能被两个进程同时占用，而且会丢登录态。

## 子代理什么时候能省时间

仅在本次任务允许使用子代理、工具可用、工作确实独立时分派。已有批量工具能一次解决的操作优先批量执行，避免每一步新增一个子代理。

- **优先分派第 1 步。** 一个子代理负责一款的公开页面采集和本地验收，或单独定位一张失败媒体。明确竞品 URL、清单与素材目录、预期格式和返回字段。每个子代理使用独立的标签页和暂存文件；浏览器会话只能单线使用时，由主代理批量提取后分派文件验收。
- **第 7–8 步可并行准备和审阅。** 主代理先锁定店铺、主题和默认底稿，分派不同目标模板的本地生成或只读比对。每个子代理只写自己的暂存模板；同一主题的远端上传、回读和同步由主代理汇总执行。CLI 的当前登录店铺是共享状态，避免多个代理同时切店或推送。
- **第 9 步主代理保存。** 可请子代理在已授权范围内匹配商品名称或独立读前台结果，返回证据。用浏览器保存商品时，由主代理核对店铺、商品 ID、目标模板和本轮授权，逐款提交。
- **第 10 步可独立核对。** 子代理可验证已保存的两个链接和目录内容。有需要分派落盘时，各自只负责不同目录。主代理确认绑定完成后才生成 `1-` 标记。

给子代理的例子：「只处理车载暖风机的公开竞品 URL。将素材写到已指定的目录，把原始 URL、清单路径、轮播和详情数量、未取得媒体及验证结果发回。店铺后台交由主代理处理。」
