# 第七步 · 创建商品详情页模板

第 7 步为本商品准备专用模板。单独执行时先在远端建立与默认商品模板逐字节一致的模板，再填写文案。无中间审查时可与第 8 步合并上传。

## 输入与产出

- 输入：本轮确认的平台和店铺、本商品的英文关键词、第 6 步核对到的商品身份。
- 产出：目标主题的专用模板路径、用于创建的底稿、本地副本和回读证据。
- 模板名用 `MMDD-英文商品关键词`，日期按用户当地日期，英文单词用连字符连接。例如 `1119-car-heater` 对应远端 `templates/product.1119-car-heater.json`。

## Shopify

用 `shopify theme list --store "$store" --no-input` 确认本轮 `.myshopify.com` 域名和主题 ID。用该主题的本地工程，或先用 `shopify theme pull --store "$store" --theme "$theme_id" --path "$stage_dir" --no-input` 拉到独立目录。已有工程时先回拉默认模板和已有的专用模板。主题比较和修改都在本地完成。

从目标主题的 `templates/product.json` 复制出 `templates/product.<模板名>.json`。已有同名模板时先比对和复用。历史 Liquid 主题沿用本主题的模板类型，按实际 `templates/product.liquid` 创建 `templates/product.<模板名>.liquid`，字段和区块也以该主题为准。

单独交付第 7 步时上传专用模板。可合并时先按第 8 步填写，再执行同一组命令。以下的 `target` 为完整主题相对路径，`stage_dir` 为本地主题目录，`verify_dir` 为新建的回读目录。

```bash
shopify theme push --store "$store" --theme "$theme_id" --path "$stage_dir" \
  --no-input --nodelete --only "$target" &&
shopify theme pull --store "$store" --theme "$theme_id" --path "$verify_dir" \
  --no-input --nodelete --only "$target"
```

本轮目标是已发布主题且允许写入时，给 push 补 `--allow-live`。回读确认文件存在且内容符合预期。若第 8 步需要本商品专用的辅助文件，也逐个列入 `--only` 并回读。主题 CLI 凭证失效时先恢复主题授权。 [Shopify 专用模板](https://shopify.dev/docs/storefronts/themes/architecture/templates/alternate-templates) · [上传](https://shopify.dev/docs/api/shopify-cli/theme/theme-push) · [回读](https://shopify.dev/docs/api/shopify-cli/theme/theme-pull)

## SHOPLINE

以下命令、schema 和回读细节用于 SHOPLINE。

## 前置一：CLI 能用，且登录的是本轮店铺

`sl` 按「凭证文件里的 currentStore」决定操作哪家店，**不看当前目录，也不看前台域名**。所以第一步永远是确认它现在是谁。

```bash
cli=$(command -v sl || true)
if [ -z "$cli" ]; then cli="$HOME/.shopline-cli/node_modules/.bin/sl"; fi
"$cli" --version
"$cli" theme list
```

`theme list` 第一行会打印 `✨List of https://<店铺>.myshopline.com themes:`，这一行的域名就是它实际在操作的店铺。**先核对这一行，再看主题列表。**

多店铺登录态用 `sl-profile` 管理（凭证在 `~/.config/configstore/shopline.json`，快照在 `~/.shopline-cli/profiles/`）：

```bash
~/.shopline-cli/sl-profile list        # 当前登录 + 已保存快照
~/.shopline-cli/sl-profile use peakoom # 切到某个快照，不用重新登录
~/.shopline-cli/sl-profile save peakoom # 登录成功后更新该店快照
```

`use` 会把切换前的状态备份成 `.previous.json`，切错了可以切回来。

### CLI 授权排查

| 现象 | 含义 | 处理 |
|---|---|---|
| `theme list` 返回 `400` 或 `AggregateError` | 当前主题列表请求失败，聚合日志可能包含遥测错误 | 先核对实际店铺和主题请求的错误。明确提示会话失效时重新授权 |
| `login --store` 返回 `400`、未打印 `authorizing` | 授权流程尚未启动 | 核对后台域名、CLI 版本和本地回调端口 |
| `socket hang up` / `ECONNRESET` | 本机出网或代理不通，请求没到服务器 | 先修网络，别改命令 |
| `Store unavailable` / `This store is currently unavailable` | 店铺域名写错 | 换正确域名，参见第 6 步 |

### 重新授权

```bash
store='example.myshopline.com'
"$cli" login --store "$store"
```

- 域名用后台域名 `<handle>.myshopline.com`，前台自定义域名不一定能通过。
- 走的是「打开浏览器授权 + 本地回调服务器」的 OAuth 流程，**必须在能弹浏览器的交互终端里跑**。成功的标志是打印 `authorizing https://...` 和 `login succeed!`。
- CLI 1.5.10 实测使用本地回调端口 `3456`。在重新授权前可用 `lsof -nP -iTCP:3456 -sTCP:LISTEN` 检查。已有监听时先识别进程，再协调释放端口。使用 CLI 原生打开的授权页，保留它生成的完整回调参数。
- 授权成功后立刻存快照：`~/.shopline-cli/sl-profile save <别名>`，下次直接 `use`，不必重复走浏览器。

快照和令牌都有有效期。恢复快照后，用 `theme list` 核对当前店铺及授权结果。

## 前置二：核对店铺和线上主题

```bash
"$cli" theme list
```

输出同时满足「店铺域名正确」和「能看到目标主题」就不用再调 `whoami`。用户未指定其他主题时，选该店铺标 `[live]` 的那个，记下 `#` 后的 ID（不含 `#`）。

## 拉取底稿与生成目标模板

`theme_id`、`target`、暂存目录按本轮实际值替换，下面的 ID 只是历史实测示例。

```bash
theme_id='6ad9b495fef45239fad4608e'
stage_dir=$(mktemp -d)
verify_dir=$(mktemp -d)
printf '暂存目录：%s\n回读目录：%s\n' "$stage_dir" "$verify_dir"
target='templates/product.1124-hand-crank-charger.json'
"$cli" theme pull --theme "$theme_id" --path "$stage_dir" --nodelete \
  --only templates/product.json theme.schema.json theme.config.json "$target"
```

- `mktemp -d` 的路径要在每次终端调用之间记住并复用，变量不会跨调用保留。
- `--nodelete` 必须带，否则会删掉暂存目录里其他文件。
- 三个底稿文件一起拉：CLI 1.5.10 缺少 `theme.schema.json` 会直接退出（实测过）。
- 目标路径这次拉不到属正常（还不存在）。若已存在，先核对用途：同一商品续跑就把它当最新底稿并另存一份给第 8 步比较；用途不明时问用户。

生成空白目标模板：

```bash
test -s "$stage_dir/templates/product.json" &&
cp "$stage_dir/templates/product.json" "$stage_dir/$target"
```

## 上传和回读

线上主题用 `--allow-live`，未发布主题去掉。

```bash
"$cli" theme push --theme "$theme_id" --allow-live --path "$stage_dir" --nodelete \
  --only "$target" &&
"$cli" theme pull --theme "$theme_id" --path "$verify_dir" --nodelete \
  --only templates/product.json "$target"
```

回拉目录实际出现默认模板和目标模板后再比对：

```bash
test -s "$verify_dir/templates/product.json" &&
test -s "$verify_dir/$target" &&
cmp "$stage_dir/templates/product.json" "$verify_dir/templates/product.json" &&
cmp "$stage_dir/templates/product.json" "$stage_dir/$target" &&
cmp "$stage_dir/$target" "$verify_dir/$target"
```

第一条确认默认模板没被改动，第二、三条确认新模板存在且与默认逐字节一致。三条都过才算建好。用 `cmp` 而不是 `diff`，缩进和末尾换行差异噪声太大。

## 与第 8 步合并上传

同店同主题、各商品均通过第 6 步、且无需审查远端空模板时，可基于同一已核对的默认模板生成不同目标文件。记录底稿及各目标路径，第 8 步的填写脚本直接使用底稿输出到尚未存在的暂存路径。

一次上传指定目标路径，再一次回拉默认模板及所有目标模板。默认模板与上传前做字节比对，最终模板逐个按第 8 步验证。续跑已有专用模板时，使用刚回拉并核实归属的当前版本作为该文件的底稿。单独验收过的空模板进入第 8 步时，也使用新的暂存输出路径，避免覆盖输入。

## 保存本地副本

验收后的模板放到 `api/themes/shopline/templates/<店铺>/product.<模板名>.json`。

**多店铺必须按店铺分目录**。两家店做同一个商品时模板名完全相同（都叫 `product.1124-hand-crank-charger.json`），放同一层会互相覆盖。

## 常见问题

| 情况 | 处理 |
|---|---|
| `theme list` 返回 400 | 先核对实际店铺与主题请求错误，再按「CLI 授权排查」继续。 |
| `theme list` 显示的不是本轮店铺 | `sl-profile use <别名>` 切换；没有该店快照就先 `login --store` 再 `save`。 |
| `login --store` 返回 400，且没有 `authorizing` | 检查后台域名、CLI 版本和本地回调端口。 |
| 新模板同名已存在 | 拉回现有文件查用途。确认是本次商品就保留其最新版本并进入第 8 步；其他商品或用途不清时先定位或确认名称。 |
| 缺少 schema/config 或没有默认模板 | 从同一主题补拉。主题结构和历史实测不同时，按实际结构定位默认商品模板。 |
| 部分失败、超时或本地与回读不一致 | 先回拉目标路径看远端实际结果，再决定是否重传；只处理仍待上传的目标。 |
| 本地有另一店的同名副本 | 按店铺分目录保存，交接时带店铺域名和远端模板路径。 |
| 上传报成功但回读没有该文件 | 核对 `--only` 的变量展开和完整 `templates/` 路径，并确认本轮主题 ID。 |

## 交给第 8 步

提供：店铺域名、主题 ID、默认底稿路径、两个配置文件、目标模板名与暂存路径。
