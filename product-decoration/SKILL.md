# 商品装修

## 适用范围

这是一套**可交接的流程文档**，不绑定某个 AI 助手、某台机器或某个操作系统。换人接手时先读 [移植与适配指南](references/移植与适配指南.md)：需要哪些能力、六个可配置环境变量、目录约定、macOS / Windows / Linux 差异、凭证放哪、给 AI 的交接提示词。

文档里混着三类内容：**通用规则**（流程、验收标准、命名，照用）、**平台事实**（1688 接口、SHOPLINE 与 Shopify CLI）、**本机实测**（店铺域名、主题 ID、代理端口、崩溃日志，只作参考，不要照抄）。

## 开工条件

- **第 1 步**需要用户给出的单个竞品商品页 URL。目标平台、店铺或 SPU 命名参数尚未确认时，可先采集公开素材和做本地准备。目标平台与店铺由用户本轮指定，竞品平台、历史店铺、浏览器登录态和 CLI 当前店铺均不能作为目标店铺依据。
- **第 2 步**需要本轮确认的完整 SPU，或用于生成 SPU 的店铺 ID、名字首字母及商品序号，用于统一 CSV 的 `Handle`。只确认尚缺的参数。已有我方商品标题、后台链接、商品 ID 或指定主题时一并记录。
- **先核对本轮范围**。完整装修按下表推进。用户只要求采集时交付第 1 步。仅装修现有商品或续跑时，复用与本轮商品和店铺匹配的验收证据，先补齐目标步骤必需的输入和前置核对。
- **按步骤自检**。查对应网络、运行时和会话。换机器或换人先看[移植与适配指南](references/移植与适配指南.md)，再参考[开工前置与验收清单](references/开工前置与验收清单.md)运行环境检查，并单独核对本轮店铺与权限。凭证只在本地使用，记录登录结果，凭证值不得进入回显、说明或交付文件。

SHOPLINE 和 Shopify 的第 7–8 步均用各自的主题 CLI 拉取、上传和回读，本地创建和编辑模板。主题凭证有效时可在终端完成。完整装修的第 9 步默认由 agent 绑定，按平台选择已验证的商品 API 或商品后台。其他平台先核对实际编辑方式，再沿用商品身份、范围与验收规则。

## 浏览器约定

默认用 **agent 专用浏览器**（脚本跨平台，profile 持久化），除非用户明确指定别的浏览器工具（例如 WorkBuddy 内置浏览器）。

```bash
python3 scripts/agent_browser.py              # 启动常驻实例（profile 与端口可用环境变量覆盖）
python3 scripts/agent_browser.py --open <URL> # 在已运行的实例里新开标签页
python3 scripts/agent_browser.py --status     # 看实例状态和当前标签页
```

- 所有站点的登录态都存在这个 profile 里（1688、店铺后台、其他），跨任务复用。哪一站失效就在窗口里登一次，**不要换 profile、不要改脚本**。
- 同一 profile 同时只能被一个进程占用，全流程共用一个实例；子代理不要再各自启一个，都连同一个端口。
- 有的浏览器工具只有导航、截图和点击，**没有执行 JS、没有 Network 监听**。抓接口、注入脚本、上传本地文件、批量取数必须用带 CDP 的浏览器。
- macOS 26/27 上不要用命令行拉起系统 Chrome：`libaperitif` 会在导航时直接杀进程（`SIGTRAP`）。其他系统可以直接用系统 Chrome 加 `--remote-debugging-port`，见移植指南第五节。

## 步骤、进入条件与验收

| 步骤 | 必须具备 | 执行规则与完成证据 |
| --- | --- | --- |
| [1. 抓竞品信息](references/01-抓竞品信息.md) · [采集附册](references/01a-商品页采集与落盘.md) | 单品 URL、竞品页面可读、采集浏览器和落盘运行时可用 | 已识别的 Shopify / SHOPLINE 版式优先用脚本，待复核字段由 agent 按页面补齐。陌生版式由 agent 采集。核对六个字段、媒体顺序和原始格式后写说明。 |
| [2. 导出单品 CSV](references/02-调用单品采集API并保存CSV.md) | 第 1 步已验收、目标平台和店铺已确认、采集站会话可用、SPU 命名参数已齐 | 先查同 URL 的可用结果或在跑任务。按单品任务导出，全部数据行的 `Handle` 改为本轮指定 SPU，其余内容保留。验收 CSV 可解析、含表头和商品记录，并且只对应本次一件商品。 |
| [3. 录入 Phalanx](references/03-调用PhalanxAPI录入商品.md) | 第 2 步验收通过、Phalanx 会话有效、上传映射与 CSV 表头匹配 | 先按完整 SPU 回查并复用已核对的记录。使用匹配的映射录入后，按内部 ID 回读并核对 SKU、规格和价格。 |
| [4. 发布到目标店铺](references/04-调用Phalanx批量发布到对应店铺.md) | 第 3 步已验收、本轮账号的站点清单与目标域名已核对 | 按商品、站点先查发布状态，再处理待发布项。逐商品、逐站点确认最终成功，记录 `rel_id` 和前台链接交第 6 步。 |
| [5. 1688 以图搜同款](references/05-在1688以图搜同款.md) | 至少一个本轮目标站点已通过第 4 步验收、第 1 步的一张清晰商品原图、1688 可访问且登录态可用 | 保存 JSON 和 CSV、搜索用图及候选链接。命中数大于零、候选列表非空且主体匹配才算搜图完成。用户确认可用货源后交第 5a 步。 |
| [5a. 补采购与 ERP 信息](references/05a-Phalanx补充采购与ERP信息.md) | 第 3 步的商品内部 ID、第 5 步选定货源、完整采购链接、已核对的人民币成本价、单件重量及供应商、产品属性和海关编码、有效 Phalanx 会话 | 沿用已导入的商品和 SKU，以现有完整商品实体构造 PUT，只修改采购与 ERP 字段。以更新接口业务码 `200` 为完成依据。 |
| [6. 核对店铺商品](references/06-核对目标店铺中的商品.md) | 该店铺已通过第 4 步验收或本轮只装修已有商品、目标店铺后台域名与读取授权可用 | 有该店铺的 `rel_id` 或商品 ID 时优先按 ID 读取。核得唯一且已上架的商品后记标题、ID、编辑页和状态。多匹配时由 agent 比对主图主体、标题关键词、规格与价格并记录依据。查不到或未上架时暂停该店铺的第 7–10 步。 |
| [7. 创建专用模板](references/07-创建商品详情页模板.md) | 第 6 步通过、英文商品关键词、目标店铺主题权限及已核对的主题 ID | 用对应平台主题 CLI 拉取底稿，本地创建专用模板，限路径上传并回读。无中间审查时可与第 8 步合并上传。 |
| [8. 填卖点与标签](references/08-填写商品信息文本与Sline.md) | 第 1 步的清单与简介、第 7 步已核对的底稿和目标路径 | 优先使用标题下简介，也可用清单里的详情原文。按实际主题的区块及字段修改本地模板，再用同一 CLI 限路径上传并回读校验。 |
| [9. 绑定商品](references/09-绑定商品详情页模板.md) | 第 8 步回读通过、第 6 步商品身份和已上架状态仍成立、已满足本轮审查安排 | agent 用第 6 步商品 ID 和第 8 步模板名完成绑定。只更新商品的模板字段，回读绑定并核对实际预览。 |
| [10. 交付与标记完成](references/10-保存链接并标记完成.md) | 本轮范围内各步骤已验收、绑定有证据、实际预览已核对并完成约定的验收、已有 `商品装修说明.md` | 复用第 9 步预览证据，只补查缺项。完整装修用 `scripts/finalize_decoration.py` 校验交付物、同步预览链接和清单、给目录加一次 `1-` 并标「全部完成」。 |

## 串行与并行

- **单款主线**为 `1 → 2 → 3 → 4`。第 4 步至少有一个目标站点成功后分两条线，`5 → 5a` 补货源和 ERP，`6 → 7 → 8 → 9` 核对店铺并装修。两条线可并行。第 6 步按已发布的店铺分别启动。等待货源确认或补齐 ERP 参数时，可继续已通过第 6 步的店铺装修。完整装修的第 10 步汇合两条线。
- **多款之间**可并行采集、下载和验收，每款使用独立标签页、清单、暂存路径和商品目录。不同商品可各自推进到已满足前置条件的步骤。
- **同店同主题**且无需中间审查时，可以并行生成不同目标模板，由同一个执行者合并一次限定路径上传、一次回拉、逐文件验收。跨店先切店并核对实际域名，再执行该店的 CLI 操作。
- **远端写入**按商品和站点核对。涉及同一 SPU 的全量更新、同一主题的推送或共享 CLI 的切店操作时串行。商品绑定逐个保存和回读，前台预览可分别核对。详见[批量执行与交接](references/00-批量执行与交接.md)。

装修段的验收与排错见[装修段总览](references/装修段总览.md)。SHOPLINE 开工前用 `sl theme list` 核对凭证当前店铺和目标主题。未指定主题时用目标店铺的 `[live]` 主题。快照和令牌均可能过期。

同一商品在两家店装修时，模板名相同（如 `product.1124-hand-crank-charger.json`），本地副本必须按店铺分目录保存，远端上传和回读也要按店铺分别执行、分别记录预览链接。卖点与标签照录采集原文，素材缺失时只能用采集到的原文、留空或请用户提供，不得改写或翻译。

素材落盘后创建 `商品装修说明.md`，记录原始竞品链接、我方平台和店铺、当前进度，以及上表各步骤的状态与完成日期。目标信息当时仍有缺项时标为「待确认」，收到确认后补齐。每步验收后更新同一文件的步骤状态和当前进度，按用户当地日期填写实际完成日期（`YYYY-MM-DD`）。未验收的步骤保留实际状态，完成日期用「—」。续跑时保留已确认的日期，历史步骤日期无据可查时标为「待核实」。

步骤 1 的提取脚本为 `assets/extract_storefront.js`。脚本和 agent 都用同一份清单，交给 `scripts/save_product_page.rb` 落盘。见[商品页采集与落盘](references/01a-商品页采集与落盘.md)。`scripts/` 与 `assets/` 必须保持同级，落盘脚本按相对路径读标签模板。

全程禁止 OCR 或转写图片内的文字。卖点和标签照录采集原文，保留标点、数字、表情和顺序。HTML 转义以及红色、加粗和换行属于排版，核对时比较解码后的原文。

素材目录最初用 `MMDD-中文关键词-英文关键词`，模板名用 `MMDD-英文商品关键词`，英文模板关键词以连字符连接。日期用用户当地日期。用户指定名称时优先使用；续跑沿用同一批商品已确定的名字。素材目录的 `1-` 完成标记按第 10 步处理。

## 审查、授权与续跑

- 用户要求逐步审查时，每步验收后停在该处等确认。用户要求绑定前审查时，完成并验收第 8 步后停在绑定前。批量合并上传适用于本轮允许跨过第 7 步单独审查的情况。
- 完整装修在第 8 步验收后由 agent 继续绑定。用户要求自绑、绑定前审查或只交付到第 8 步时，按约定交接。
- 续跑先核对原始 URL、商品身份、店铺和现有证据。保存、上传、提交状态不明时，先回读任务、商品或模板，再仅重试未完成的操作。
- 结束时逐商品逐店报告模板上传、商品绑定、前台核验和本地完成标记。完整装修另记录货源确认及 ERP 更新结果。每个阻塞项写明商品、实际步骤、证据及待补输入，同时保留已经验收的成果。历史做法见[暖风机与激光焊机实测](references/批量实测-暖风机和激光焊机.md)。
